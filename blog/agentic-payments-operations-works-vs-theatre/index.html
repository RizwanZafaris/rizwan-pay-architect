Agentic Payments Operations: What Actually Works, and What's Theatre

Every vendor pitch in 2025 has "agentic" somewhere on the slide. Most of the demos are theatre — a scripted scenario in which the agent makes the exact decision the demo was rehearsed around, in a context that does not exist in production. The product-manager audience nods politely. The buyer signs anyway because the board is asking what the company's AI agent story is.

Behind the marketing, a real productive subset exists. There are 5–6 operations workflows in payments where an LLM-driven agent — given the right tools, the right guard rails, and the right operating frame — earns its keep. There are 4–5 more where the demo is theatre and the production deployment ranges from useless to dangerous.

This is the honest operator read on the difference. Where agents work, what makes them work, where they fail, and what makes them fail.

A short definition

An "agent" in this context is an LLM-driven workflow that:

  • Takes a goal expressed in natural language
  • Has access to a set of tools (APIs, databases, internal systems)
  • Plans a sequence of actions to achieve the goal
  • Executes the actions
  • Observes the results and adjusts

Compare this to a non-agentic LLM call: single input, single output, no tools, no plan, no iteration. The "agentic" claim adds the planning loop, the tool use, and the iterative execution.

In payments operations, the question is whether the planning loop produces better outcomes than a deterministic workflow would. Sometimes yes; sometimes no; the distinction is in the workflow's properties.

Where agentic ops genuinely earn their keep

1. Dispute case enrichment

The workflow. A chargeback lands. The agent gathers evidence: pulls the original transaction, the cardholder's prior transaction history, the merchant's product catalogue, the device fingerprint, the IP geolocation, the delivery confirmation if any, the cardholder's communications. It assembles a case file. It drafts the representment language.

Why agents fit. The work is evidence gathering across multiple systems in a partially-templated structure. Each chargeback is slightly different (different reason code, different merchant, different prior-transaction shape). The agent's planning loop is the right fit because the next step depends on what the previous step found.

The lift. The case-investigator's per-case time drops from 25-40 minutes to 5-10 minutes of review. The agent does not make the final decision; the investigator confirms and submits.

The guard rail. The agent never submits the representment. It produces the draft and the evidence pack; a human investigator confirms.

2. AML alert triage

The workflow. An AML alert fires (sanctions match, unusual transaction pattern, structuring suspicion). The agent gathers the entity profile, prior transaction patterns, public-record information, news mentions, related entities. It triages the alert: clean false positive (e.g., name collision with a high-confidence non-match), needs investigator review, or needs escalation to compliance.

Why agents fit. Triage is a multi-source synthesis task. The decision logic is "given these facts, which bucket?" — a classification problem with structured-output discipline that LLMs handle competently.

The lift. Tier-1 analyst throughput roughly doubles. Clean false positives are auto-dismissed (with audit log); real cases get to investigators with the context already gathered.

The guard rail. The agent never dismisses a sanctions hit — only flags as "appears to be name collision, suggest dismissal". Human confirms. The audit trail of agent + human decision is regulator-facing.

3. Merchant-support level-1 triage

The workflow. A merchant raises a support ticket. The agent reads the ticket, queries the merchant's recent transactions, account status, settlement history, recent alerts. It produces either an auto-response (for FAQ-class tickets where the agent has high confidence) or a triage note for the support analyst with the relevant context pre-pulled.

Why agents fit. Support ticketing is a high-volume routing problem with merchant-context lookup. The agent's tool use (reading the merchant's actual state, not just the ticket text) produces better triage than text-only classification.

The lift. Tier-1 throughput doubles or triples on the auto-response slice. Tier-2 analyst time per case drops because the context is pre-pulled.

The guard rail. Auto-response only on tickets where the agent's confidence exceeds a calibrated threshold AND the category is on the "auto-respond safe" list. Everything else routes to humans.

4. Settlement-break investigation

The workflow. A reconciliation break appears. The agent pulls the affected transaction, the merchant's recent settlement history, the scheme settlement file, the bank statement entry (or absence thereof). It produces a diagnostic: most likely cause, evidence supporting that diagnosis, recommended fix.

Why agents fit. Settlement-break investigation is a structured detective workflow — pull data, compare, hypothesise, validate. The agent does the pulling and comparing; the human reviews and decides on the fix.

The lift. Investigator time per break drops from 15-30 minutes to 3-5 minutes of review and decision.

The guard rail. The agent never fixes the break (does not write to the ledger). It produces the diagnostic; a senior reconciliation analyst applies the fix.

5. Onboarding document follow-up

The workflow. A KYB submission is missing a document or has a low-confidence extraction. The agent identifies what is missing or unclear, drafts a follow-up message to the merchant explaining what is needed in their language, in a tone appropriate to the platform.

Why agents fit. The work is a structured-output writing task with context (which document is missing, what merchant tier they're in, what tone the platform uses). Templated follow-ups are too rigid; case-by-case human writing is too slow.

The lift. Onboarding ops time per follow-up drops from 8-15 minutes to under a minute (review and send). Cycle time on document re-requests drops.

The guard rail. The follow-up message is a draft until a KYB analyst reviews. Auto-send is reserved for the very narrow case of a single missing standard document with no ambiguity.

Where the agentic demo is theatre

1. "Agent decides whether to approve a transaction"

The demo is impressive: cardholder pays, agent considers fraud signals, agent makes a decision in 200ms. In production, this is a fraud-decision rule engine plus an LLM wrapper that adds nothing — the rule engine was already real-time, the LLM adds latency without improving accuracy, and the regulator wants to know exactly how the decision was made. Real fraud decisioning is classical ML + rules; agents do not belong on the auth path.

2. "Agent processes the entire chargeback end-to-end"

A subset of demos show the agent reviewing, gathering, and submitting the chargeback response. In production, no compliance team will allow the agent to submit on its own — the legal liability and the regulator-facing audit posture are too sensitive. The agent's role is enrichment and drafting; submission is human.

3. "Agent autonomously onboards a merchant"

The demo shows the agent extracting documents, screening, adjudicating, and approving. In production, the screening engine is separate, the adjudication is human, and the approval has formal sign-off. The agent does extraction + first-pass routing; the rest is not agent work.

4. "Agent writes the new product feature"

A class of demo shows the agent reading a PRD, drafting code, deploying to production. In a regulated platform, the engineering review, the code review, the test coverage, the deployment governance, and the rollback discipline make the "agent ships code" demo theatre. The agent might draft code; the engineering team ships it.

5. "Agent manages the regulator relationship"

The most dangerous theatre. Regulators have explicit guidance that automated systems making consequential decisions must have human accountability. An agent that drafts regulator submissions, attends meetings (via assistants), or makes representations is not a productive workflow — it is a compliance incident in waiting.

The architectural pattern that separates real from theatre

Five properties of agent workflows that actually ship in payments:

1. The agent has a tightly scoped goal. "Enrich this chargeback case" is scoped. "Handle the disputes function" is not. Agents that work have one goal per workflow, not a goal hierarchy.

2. The agent uses tools, not just text. Agents that only generate text are not agents in the sense that matters — they are LLM calls. The productive agents are integrated with the platform's actual systems (read the transaction, read the merchant profile, read the screening result).

3. The agent's output is a draft, not a decision. The productive pattern is: the agent produces a recommendation with evidence; a human confirms. The exceptions are narrow (high-confidence auto-dismissal of clear false-positive sanctions hits, auto-responses to clearly-templated support tickets) and audited.

4. The agent's decisions are auditable per-step. Every tool call, every intermediate output, every reasoning step is logged. The regulator inquiry "show me how the agent decided" is answerable with a query.

5. The human-in-the-loop is permanent. Throughput improves; reviewer count does not drop to zero. The pattern is "humans review more cases per hour" not "humans are out of the loop". The platforms that ship the latter ship regulator findings.

What to ask vendors

A working set of questions to separate productive agent workflows from theatre during a vendor evaluation:

  • What is the goal scope of the agent? If it includes more than one operational function, it is too broad.
  • What tools does the agent have access to? If the list is generic ("internet search, code execution"), it is not designed for your platform.
  • What is the human-in-the-loop pattern? If the answer is "agent makes the decision; human reviews if escalated", the threshold for escalation is doing the work.
  • What is the audit posture? If the vendor cannot show a regulator-facing audit log of agent decisions, the platform's compliance function will reject the deployment.
  • What is the failure mode? When the agent gets it wrong, who is liable and what is the recovery path?
  • Show me a real customer in production for >6 months. Demos are theatre. Six months of production data separates the use cases that work from the ones that drift.

The vendors that have shipped real agentic ops can answer all six concretely. The vendors selling theatre cannot.

The senior-PM tell

The interview question that distinguishes senior PMs on agentic AI: "your CEO wants us to deploy an agent for X. Walk me through how you decide if it is real or theatre."

The junior answer talks about ROI estimates. The senior answer reads: what is the scope; what are the tools; what is the failure mode; what is the human-in-the-loop posture; what is the audit pattern; can a regulator inquiry on agent decisions be satisfied in 30 minutes. If all six answers line up, ship the pilot. If two or three are weak, deploy with extra guard rails and reduced scope. If four or more are weak, kill it.

That answer is the operating posture. It is also the answer that prevents the AI programme from becoming the next year's regulator finding.

FAQ

Are these the only productive agentic workflows in payments? The five above are the most consistently-productive that I have seen across multiple platforms. Other niches exist (treasury reconciliation enrichment, vendor-management ticketing, internal-audit pre-prep) but the pattern is the same: scoped goal, tool use, draft output, human confirmation, auditable trail.

Will agents take over more of these workflows over time? Slowly. The bottleneck is not the agent capability; it is the regulator posture and the platform's appetite for liability shift. As model performance improves and as regulators issue clearer guidance, the human-in-the-loop threshold will move — but slowly, and asymmetrically per jurisdiction.

What is the right vendor vs. build call? For workflow-specific agents (dispute enrichment, AML triage, onboarding follow-up), specialised vendors are typically ahead of in-house builds. For platform-deep workflows (settlement-break investigation, merchant-support triage that requires deep internal-system access), in-house builds usually win because the tool-integration matters more than the LLM choice.

How do agents interact with the seven ML-failure patterns? Pattern overlap. Concept drift applies (agent prompts decay as systems change). Label leakage applies (training the agent on outcomes that include human-review changes). Ops integration applies (the agent's output has to land cleanly in the reviewer's workflow). All seven patterns from the Why AI/ML Solutions Fail in Production Payments essay apply to agentic systems too.

What's the cost? Per-action LLM cost is real but rarely the binding constraint. The binding constraint is the integration and audit engineering: the tool integrations, the audit logging, the human-review tooling, the failure-mode handling. A productive agentic workflow takes ~3-6 engineering months of integration work to ship cleanly; the ongoing LLM cost is small in comparison.

How is this different from RPA? RPA (robotic process automation) is rigid — it executes the same screen-clicks every time. Agents handle variation: different chargeback shapes, different document classes, different merchant contexts. RPA works for fully-deterministic workflows; agents work for partially-deterministic ones. Many platforms use both — RPA for the fixed parts, agents for the variable parts.
